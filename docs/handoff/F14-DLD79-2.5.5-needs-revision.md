# F14 DLD rev79 §2.5.5 needs a design revision

F14 DLD rev79 §2.5.5 keeps the migration steps that were already applied when a later step fails, and
resumes from the committed revision on the next start. F15 HLD rev116 §2.3.3.5 and DLD rev70 §2.6
(FR8.HD1.app-db.DD1, FR8.HD1.app-host.DD1) require a full restore of the pre-migration backup.

The user decided to follow F15 (WP6, branch codex/f15-wp6-migration-restore). The code restores the
whole database from the pre-migration backup on Windows, Linux and macOS. F14 DLD79 §2.5.5 and its
test expectation ("failed_definition_preserves_completed_backup_and_restart_uses_next_sequence" for
the multi-step run) must be revised to match.

Open design points for the revision:

- The restore is performed in place through SQLite's backup API, so the database file keeps its
  identity (pinned handle, macOS path identity). The F15 text "atomically restore over the live
  database including WAL and SHM" is met by one destination transaction followed by a truncating
  checkpoint; no file swap is done.
- Interrupted migrations and restores are recorded in db-backups/migration-journal.json. A finished
  restore leaves db-backups/restored-<sequence>.json as the record. Neither name is part of the F14
  backup naming rules yet.
- No separate reason key exists for a failed restore. Startup reports startup.migration_failed and
  names db.restore_failed in the message text. The design should either add a key or confirm this.
