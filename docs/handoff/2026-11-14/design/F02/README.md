## 기존 화면 문제 두 건의 판단 (2026-11-15, F02가 VM에서 발견)

화면을 직접 보지 않고 정한 규칙이다. 반영 뒤 캡처로 확인한다.

### 1. 이름의 앞뒤 공백

이름이 공백으로 시작하거나 끝나면 그 공백을 보이게 표시한다. "보고서"와 "보고서 "는 서로 다른 항목이고, 구별되지 않으면 사용자가 엉뚱한 쪽을 고르거나 정리한다.

- 이름의 맨 앞과 맨 끝에 있는 공백 문자를 하나마다 "␣"(U+2423)로 그린다. 흐린 글자색을 쓰고 이름 글자와 같은 크기로 둔다. 예: `보고서␣`, `␣␣초안`.
- 대상은 공백, 탭, 줄바꿈 없는 공백(U+00A0)과 그 밖의 유니코드 공백이다. 이름 가운데의 공백은 그대로 둔다. 공백만으로 된 이름은 전부 표시한다.
- 따옴표와 가운데 점은 쓰지 않는다. 둘 다 실제 이름에 들어갈 수 있는 글자다.
- 표시는 화면에만 있다. 경로 복사, 내보내기, 검색, 정렬은 실제 이름을 쓴다.
- 포인터를 올리거나 초점이 가면 설명을 보인다: "이름 끝에 공백이 N개 있습니다" / "The name ends with N spaces", "이름 앞에 공백이 N개 있습니다" / "The name starts with N spaces". 화면 낭독기에는 이름 뒤에 같은 설명을 붙여 읽게 한다. 기호 자체는 읽지 않게 한다.
- 이름이 나오는 모든 곳에 같은 규칙을 쓴다: 탐색 표, 항목 상세의 제목, 경로의 마지막 마디, 알림 문구 속의 이름. 공통 부품 하나로 만든다.
- 끝이 점인 이름은 점이 보이므로 따로 표시하지 않는다.

### 2. 이름표가 한 글자씩 꺾이는 것

이름표와 값이 한 줄에 놓이는 모든 줄에 적용한다. 공통 부품(`Readout`)에서 고친다.

- 이름표는 줄어들지 않고 줄바꿈하지 않는다(한국어는 낱말 중간에서 끊지 않는다).
- 값이 남은 너비를 쓴다. 값은 줄바꿈할 수 있고, 경로는 구분 기호 뒤에서 먼저 끊는다.
- 값에 쓸 너비가 12글자 폭보다 좁아지면 이름표를 윗줄, 값을 아랫줄로 쌓는다. 쌓였을 때 값은 왼쪽 정렬이다.
- 가운데 줄임 경로 부품이 생기면 경로 값은 그 부품으로 바꾼다.

## 고대비 모드의 비활성 표시 (PR #62 초안의 판단 요청, 2026-11-15)

## 스캔 중 탐색 표의 자동 반영과 폴더 기준 "먼저 분석" (2026-11-15, 사용자 결정)

사용자 결정: (1) 스캔 중 탐색 표는 새 결과를 자동으로 반영하고, 사용자가 고르거나 스크롤하는 동안에는 미룬다. (2) "먼저 분석" 요청은 결과 판이 아니라 폴더를 가리킨다. 발행 설계 FR3.HD1.gui-web.DD1("새 판은 사용자가 갱신을 고를 때부터 쓴다")과 다르므로 설계 문서 개정이 필요하다. F02가 PR #63 병합 뒤 착수한다.

아래는 디자인팀이 정한 화면 규칙이다. 그림과 캡처로 확인하지 않은 규칙이며, 구현 캡처로 검수한다. 구현하다 맞지 않는 곳이 있으면 디자인팀에 알린다.

### 1. 무엇을 언제 반영하는가

반영할 것을 둘로 나눈다. 값이 바뀌는 것은 누르려는 대상을 움직이지 않으므로 미루지 않는다.

| 바뀌는 것 | 반영 | 빈도 |
| --- | --- | --- |
| 보이는 행의 값(크기, 상태 문구, 머리의 항목 수) | 항상 제자리에서 바로 | 1초에 한 번 이하 |
| 자리가 바뀌는 것(행의 순서, 새 행, 사라진 행) | 아래 "미루는 조건"이 없을 때 | 2초에 한 번 이하 |

스캔은 1초 이상의 간격으로 새 결과를 낸다(9번의 정정 참고). 화면은 위 빈도보다 자주 바꾸지 않는다. 표가 계속 흔들리면 읽을 수 없다.

### 2. 자리 이동을 미루는 조건

하나라도 해당하면 자리 이동을 미룬다. 값은 계속 바뀐다.

- 포인터가 표 위에 있다(행 단추를 누르려는 순간에 행이 움직이면 엉뚱한 행을 누른다).
- 스크롤하는 중이거나 스크롤이 멈춘 지 1초가 안 됐다.
- 키보드 초점이 표 안에 있고 마지막 키 입력 뒤 2초가 안 됐다.
- 선택된 행이 있다.
- 행 메뉴, 항목 상세, 대화상자가 열려 있다.

조건이 모두 없어지면 미뤄 둔 자리 이동을 한 번에 반영한다.

### 3. 안내 표시

- 미뤄 둔 자리 이동이 있을 때만 선택 동작 줄의 문구 끝에 덧붙인다: "새 항목이 N개 있습니다" / "N new items are waiting"(9번 참고). 같은 줄에 "지금 반영" / "Apply now" 단추를 둔다. 선택이 있어 오래 미뤄질 수 있으므로 사용자가 직접 반영할 길이 필요하다.
- 미뤄 둔 것이 없으면 아무 표시도 하지 않는다. 자동으로 반영될 때마다 알림을 띄우지 않는다.
- 화면 낭독기에는 자동 반영을 읽어 주지 않는다. "지금 반영"을 눌렀을 때만 "최신 결과를 반영했습니다" / "Latest result applied"를 한 번 알린다.
- PR #60의 "새 결과가 있습니다 · 최신 결과로 바꾸면 먼저 분석할 수 있습니다"와 "최신 결과 보기"는 스캔이 진행 중일 때 나타나지 않는다.

### 4. 반영할 때 지키는 것

- 선택은 같은 항목에 남는다. 항목이 사라졌으면 선택을 풀고 줄의 문구가 바뀐다.
- 초점은 같은 항목에 남는다. 항목이 사라졌으면 같은 자리의 행으로 간다.
- 스크롤은 화면 맨 위에 보이던 행을 기준으로 고정한다. 위쪽에 새 행이 끼어들어도 보던 행이 밀려나지 않는다.
- 행이 자리를 옮길 때는 200ms 안에 미끄러지듯 움직인다. 값은 숫자만 바뀌고 깜박이지 않는다. 움직임 줄이기 설정이면 모두 즉시 바뀐다.
- 행 높이는 값이 바뀌어도 그대로다.

### 5. 폴더 기준 "먼저 분석"

- 스캔이 진행 중이거나 일시정지 중이면 선택 동작 줄, 행 단추, 행 메뉴의 "먼저 분석"을 항상 쓸 수 있다. 표가 조금 전 결과를 보이고 있어도 같다.
- "먼저 분석 요청됨"과 "먼저 분석하는 중" 표시는 자동 반영 뒤에도 같은 폴더에 남는다.
- 요청한 폴더가 더 이상 스캔 범위에 없으면 알림으로 알린다: "‘영상’ 폴더를 찾을 수 없어 먼저 분석하지 못했습니다" / "Couldn't find ‘Videos’, so it wasn't analyzed first".

### 6. 스캔이 멈추거나 끝났을 때

- 일시정지: 마지막 결과까지 반영한 뒤 멈춘다. 미뤄 둔 자리 이동이 있으면 3번의 안내가 남는다.

"결과 판: 중간 결과"와 상태 표지("스캔 중", "스캔 일시 중지됨", "스캔 완료")는 그대로 둔다.

그 밖에:

- 큰 숫자가 바뀔 때 주변 배치가 흔들리지 않는다. 숫자는 폭이 같은 숫자 글꼴로 그리고, 단위가 바뀌어도(KiB → MiB) 줄 높이는 그대로다. 숫자를 굴리는 식의 움직임은 넣지 않는다.
- 화면 낭독기에는 값이 바뀔 때마다 읽어 주지 않는다. 상태가 바뀔 때(일시 중지, 완료)만 지금처럼 알린다.
- 스캔이 끝나면 최종 결과를 자동으로 반영하고 "결과 판: 최종"으로 바뀐다.
- 자동 반영은 진행 중인 스캔의 결과를 보고 있을 때만 한다. 이전 스캔의 결과를 보고 있는데 다른 스캔이 새 결과를 낸 경우에는 지금처럼 알리고 사용자가 "최신 결과 보기"로 고른다. 탐색 표도 같다.
- 분석 화면에 그래프가 연결되면(F06) 그래프도 같은 박자로 자란다. 그때 이 절을 F06 규칙과 맞춘다.

검수 때 받을 캡처(Light·Dark): 스캔 실행 중의 요약(바뀐 둘째 줄, "최신 결과 보기" 없음), 일시 중지, 완료 직후, "측정 상세"를 펼친 채 값이 바뀐 뒤의 모습. 5초쯤의 화면 녹화 하나.

### 9. 구현 가능 여부와 순서 (2026-11-15, F02의 답)

- 분석 화면 요약(8번): 계약을 바꾸지 않고 구현할 수 있다. F02가 PR #63 병합 뒤 먼저 진행한다. 검사 문제 목록은 루트·경로 순이라 탐색 표의 2~4번 규칙을 쓴다.
- 탐색 표(1~4번)와 폴더 기준 "먼저 분석"(5번): 지금 구조로는 화면만으로 구현할 수 없다. 행을 가리키는 번호가 결과마다 다시 매겨져 새 결과에서 같은 행을 알아볼 수 없고(표시 이름으로 맞추는 것은 계약이 금한다), 엔진이 루트가 아닌 폴더를 새 결과에서 다시 열어 주지 않는다. 미루는 동안 표 전체를 그대로 두는 방식도 반영하는 순간에 같은 것이 필요하다.
- 필요한 것: 엔진이 폴더와 행마다 결과가 바뀌어도 같은 값인 키를 내주고, 그 키로 같은 폴더를 새 결과에서 열 수 있게 하는 계약 추가. F02가 설계 개정안과 표준화 팀 검토를 준비한다. 디자인팀은 1~4번 규칙을 그대로 둔다. 이 계약은 사용자가 결정한 동작의 전제이므로 뒤로 미루는 일로 다루지 않는다.
- 그때까지의 탐색 표: PR #60의 동작이 남는다("새 결과가 있습니다 …"와 "최신 결과 보기"). "최신 결과 보기"를 누르면 범위 루트로 돌아가고 선택, 스크롤, 초점이 사라진다. 사용자가 결정한 동작이 아직 아니라는 점을 릴리스 판단 때 밝힌다.

사실 정정과 그에 따른 규칙 보완:

- 스캔이 새 결과를 내는 간격은 최소 1초다. 이 문서 앞부분의 "0.2~0.5초마다"는 F02가 처음 알린 값이고 틀렸다(그 값은 "최신 결과 보기"를 누른 때부터 다음 게시까지 남은 시간이었다). 1번의 빈도 규칙(값 1초, 자리 이동 2초)은 그대로 맞는다.
- 지금 표는 경로 순으로만 정렬되고 정렬 선택이 없다. 그래서 스캔 중의 자리 이동은 새 행이 끼어드는 것과 행이 사라지는 것뿐이고, 기존 행끼리의 순서는 바뀌지 않는다. 3번의 안내 문구를 사실에 맞춘다: "새 항목이 N개 있습니다" / "N new items are waiting". "바뀐 순서"는 정렬 선택이 생길 때 다시 넣는다.

### 10. 표준화팀 규칙 "한 목록은 한 판의 행만 보여 준다"와의 관계 (2026-11-15)

표준화팀이 제안한 규칙: 한 목록은 한 결과 판의 행만 보여 준다. 옛 판의 행과 새 판의 행을 섞지 않는다. 옛 판을 보존하지 않는다.

디자인팀 판단: 이 규칙에 동의한다. 사용자에게도 이롭다(한 화면의 숫자가 서로 다른 시점의 값이면 합이 맞지 않는다). 자동 반영의 목적(값은 계속 새로워지고, 누르려는 대상은 움직이지 않는다)과 충돌하지 않는다. 다만 앞의 규칙 가운데 세 곳이 문구대로면 이 규칙과 어긋나므로 아래로 고친다. 이 절이 2·3·4·8번의 해당 부분을 대신한다.

고치는 것:

1. "자리 이동을 미룬다"의 뜻. 옛 판의 행 배치를 계속 보이는 것이 아니다. 표는 항상 가장 새 판으로 넘어간다. 미루는 동안에는 그 새 판의 행 가운데 화면에 아직 없던 행(새 항목)을 보이지 않게 둘 뿐이다. 보이는 행은 모두 같은 판에서 온다.
2. 사라진 행. 새 판에 없는 행은 미루는 중에도 바로 사라진다. 옛 판의 값을 붙들고 있을 수 없기 때문이다. 스캔 중에는 드문 일이다. 사라질 때 화면 맨 위에 보이던 행을 기준으로 스크롤을 고정해 보던 곳이 튀지 않게 한다. 선택했거나 초점이 있던 행이 사라지면 4번대로 선택을 풀고 초점을 같은 자리의 행으로 옮긴다.
3. 분석 화면 요약에서 글자를 선택하는 동안(8번). 선택한 값 하나만 멈추면 요약 안에 서로 다른 판의 값이 나란히 놓인다. 선택하는 동안에는 요약 전체를 멈추고, 선택을 풀면 전체를 가장 새 판으로 바꾼다. 멈춘 값은 화면이 이미 받은 값이며 엔진에 옛 판을 붙잡아 두지 않는다.
4. 대화상자(8번의 "연 시점의 결과에 고정"). 대화상자는 열 때 받은 값을 그대로 보인다. 엔진에 옛 판을 붙잡아 두지 않는다. 펼칠 때 더 읽어야 하는 부분("진단 사유", "더 많은 관측 속성", "전체 경로" 등)을 여는데 그 사이 판이 바뀌었으면, 대화상자 전체를 가장 새 판으로 다시 읽고 맨 위에 한 줄로 알린다: "최신 결과로 바꿨습니다" / "Updated to the latest result". 한 대화상자 안에서도 판을 섞지 않는다.

그대로인 것:

- 보이는 행의 값은 1초에 한 번 이하로 제자리에서 바뀐다. 이제 "보이는 행 전체가 새 판으로 넘어간다"는 뜻이다.
- 미루는 조건(2번의 다섯 가지), 안내 문구와 "지금 반영"(3번), 선택·초점·스크롤 유지(4번), 폴더 기준 "먼저 분석"(5번).
- "지금 반영"과 자동 반영은 숨겨 둔 새 항목을 보이게 하는 일이다. 판을 바꾸는 일이 아니다.

구현 쪽에서 지켜야 할 화면 조건 (방법은 F02가 정한다):

- "더 불러오기"로 여러 쪽을 불러온 표도 한 판만 보인다. 판이 넘어갈 때 스크롤해서 보이지 않는 구간을 옛 판 값으로 남겨 두지 않는다. 그 구간으로 스크롤하면 그때의 판에서 읽고, 읽는 동안에는 행 높이가 같은 자리 표시를 보인다.
- 안내의 "새 항목이 N개 있습니다"에서 N을 싸게 셀 수 없으면 "새 항목이 있습니다" / "New items are waiting"으로 쓴다.
- 탐색 머리의 항목 수는 판 전체의 수다. 숨겨 둔 새 항목이 있으면 표에 보이는 행 수보다 많을 수 있고, 안내 문구가 그 차이를 설명한다.

표준화팀에 부탁하는 문구: "목록에 보이는 행은 모두 같은 판에서 온다. 그 판의 행 일부를 아직 보이지 않게 두는 것은 허용한다." 이 둘째 문장이 없으면 미루는 동안 새 항목을 숨길 수 없고, 누르려는 행이 포인터 아래에서 밀려난다.

표준화팀의 답 (2026-11-15): 둘째 문장을 받아들였다. 정식 검토 문안은 세 문장이다.

1. 목록에 보이는 행은 모두 같은 결과 판에서 온다.
2. 화면은 그 판의 행 일부를 아직 보이지 않게 둘 수 있다.
3. 위치·구간·합계를 쓰는 요청과 응답은 화면에 보이는 배치가 아닌 그 판 전체의 순서와 수를 기준으로 한다.

디자인팀은 세 문장과 따라 나오는 조건에 동의한다. 화면 규칙에 더하는 것:

- 보이는 행은 새 판에서 다시 읽은 행이다. 옛 판의 행에 값만 덧씌우지 않는다. 그 행의 상세 보기, 경로 복사, "먼저 분석"은 현재 판으로 동작한다.
- 숨겨 둔 새 항목은 선택, 초점, 동작의 대상이 아니다. Shift로 고르는 범위 선택과 전체 선택에 들어가지 않고, 화살표 키는 건너뛴다. "항목 N개 선택됨"의 N은 보이는 행만 센다. "지금 반영" 뒤에 나타난 행은 선택되지 않은 상태다.

열어 둔 것 (정렬 선택이 생길 때 다시 정한다): 크기처럼 값에 따라 바뀌는 정렬이 화면에 생기면 판이 넘어갈 때 기존 행끼리도 순서가 바뀐다. 그때 디자인팀이 필요로 할 것은 "미루는 동안 보이는 행의 순서를 그대로 둔다"이다. 이 경우 화면의 순서가 판의 순서와 달라지므로, 셋째 문장(요청과 응답은 판의 순서 기준)과 함께 화면 규칙을 다시 정한다. 정렬 UI를 넣는 쪽은 그 전에 디자인팀과 표준화팀에 알린다.

### 11. 설계 개정 초안의 질문 세 건 (2026-11-15, Q13 · Q14 · Q17)

디자인팀은 개정 초안 본문을 읽지 못했다(이 대화에서 AIDA 도구를 쓸 수 없었다). 총괄이 전한 질문 문구만 보고 정했다. 초안의 전제와 다르면 F02가 알린다.

**Q13. IF-08 구현 전 "먼저 분석 요청됨" 표시가 풀리는 조건**

표지는 쓴다. 표지가 없으면 요청이 받아들여졌는지 알 수 없다. 풀리는 조건은 화면이 알 수 있는 사실에만 건다.

| 때 | 표지 |
| --- | --- |
| 다른 폴더를 요청함 | 새 폴더로 옮긴다(PR #45에서 정한 대로) |
| 스캔이 끝남(완료, 취소, 실패) | 푼다 |
| 일시 중지 | 그대로 둔다 |
| 그 폴더의 수집이 끝남 | IF-08이 생기면 푼다. 그 전에는 화면이 알 수 없으므로 조건으로 쓰지 않는다 |

문구는 엔진이 확인해 준 것만 말한다. "먼저 분석하는 중"은 엔진이 지금 그 폴더를 우선 영역으로 알려 주는 동안에만 쓴다. 그 폴더의 수집이 끝난 뒤에도 엔진이 계속 우선 영역으로 알려 준다면, IF-08 전에는 "먼저 분석하는 중"을 쓰지 않고 "먼저 분석 요청됨"만 쓴다. 끝난 폴더에 "하는 중"이라고 말하는 것은 틀린 안내다.

Q13 보완 (2026-11-15, F02의 확인): 엔진은 그 폴더 아래의 남은 작업이 0이 되면 우선 영역을 스스로 풀지만, 그 사실을 화면에 알리는 길은 IF-08이 생겨야 있다. 그래서 지금 병합된 화면(PR #45)은 수집이 이미 끝난 폴더에도 "먼저 분석하는 중"을 스캔이 끝날 때까지 보일 수 있다. 틀린 안내다. 결정:

- IF-08 전에는 행의 표지로 "먼저 분석하는 중"을 쓰지 않고 "먼저 분석 요청됨"만 쓴다. 알림 문구 "‘영상’ 폴더를 먼저 분석합니다"는 응답을 받은 순간의 사실이므로 그대로 둔다.
- 이 수정은 폴더 기준 "먼저 분석" 구현을 기다리지 않는다. 문구 조건 하나를 바꾸는 일이므로 따로 낸 작은 PR로 먼저 고친다. 계약 검토가 길어지는 동안 틀린 안내가 남지 않게 한다.
- IF-08이 생기면 "먼저 분석하는 중"을 다시 쓰고, 그 폴더의 수집이 끝나면 표지를 푼다.

PR #70 검수 (2026-11-15, 초안, head 2a0dbb7e, 캡처 36cd5c7a의 Light 한 장): 디자인 쪽은 병합에 동의한다. 고칠 것은 없다.

- 요청한 뒤 스캔을 다시 시작한 상태에서 "영상" 행의 표지가 "먼저 분석 요청됨"이다. "먼저 분석하는 중"은 보이지 않는다.
- 표지가 다른 폴더를 요청하면 옮겨지고, 일시 중지에서 남고, 스캔이 끝나면 풀리는 것은 캡처가 없고 시험으로만 확인됐다. 스캔이 끝난 뒤의 모습은 화면으로 볼 수 없다(끝난 뒤에는 이전 결과의 표를 열 수 없다).
- Dark는 보지 못했다.

**Q14. "새 항목이 N개 있습니다"의 N**

N을 쓰지 않는다. 문구는 항상 "새 항목이 있습니다" / "New items are waiting"이다.

- 불러온 구간만 센 수를 전체처럼 보이면 틀린 숫자다. 사용자가 "지금 반영"을 누를지 정하는 데 개수는 필요하지 않다. N을 위한 계약 추가는 하지 않는다.
- 안내를 보이는 조건은 정확하게 둔다: 불러온 구간 안에 숨겨 둔 새 행이 하나라도 있을 때만 보인다. 전체 수의 차이로 판단하지 않는다. 불러온 구간 밖의 새 행은 숨긴 것이 아니라 아직 불러오지 않은 것이고, 더 불러오면 나타난다.
- 3번과 9번의 "새 항목이 N개 있습니다"를 이 문구로 대신한다.

**Q17. 보던 폴더가 새 판에서 사라졌을 때**

가장 가까운 남은 상위 폴더로 간다. 범위 루트로 보내지 않는다(사용자가 내려온 길을 다 잃는다). 남은 상위 폴더가 없으면 범위 루트 목록으로 간다.

- 미루지 않는다. 사라진 폴더는 새 판에 없고 옛 판은 남아 있지 않다.
- 안내는 사라지지 않는 줄로 보인다(4초 알림으로 하지 않는다. 화면이 스스로 옮겨 간 이유를 놓치면 안 된다). 스캔 중이면 선택 동작 줄의 문구 자리에, 아니면 표 위의 안내 띠에 둔다. 사용자가 다른 폴더로 가거나 닫으면 없어진다.
  - "‘영상’ 폴더가 최신 결과에 없어 ‘민서’ 폴더를 보여 줍니다" / "‘Videos’ is no longer in the latest result. Showing ‘민서’."
  - 범위 루트 목록으로 간 경우: "‘영상’ 폴더가 최신 결과에 없어 처음 위치를 보여 줍니다" / "‘Videos’ is no longer in the latest result. Showing the top level."
- 상태 영역으로 같은 문구를 한 번 알린다.
- 초점: 표 안에 있었으면 옮겨 간 폴더 표의 첫 행으로 간다. 표 밖(머리의 단추 등)에 있었으면 옮기지 않는다.
- 선택은 푼다. 열려 있던 행 메뉴는 닫는다. 열려 있던 항목 상세는 10번의 4대로 받은 값을 보이고, 닫으면 초점이 옮겨 간 폴더 표의 첫 행으로 간다.
- 이동줄(상위 폴더 단추들)은 옮겨 간 폴더까지로 줄어든다.

HLD 2.3.4의 와이어프레임 블록에 남은 옛 문구는 개정 때 이 README의 문구로 바꾼다. 기준 문구가 있는 곳: 선택 동작 줄의 사유와 알림(PR #45 검수 절), 자동 반영의 안내와 "지금 반영"(3번과 이 절의 Q14), 분석 화면 요약의 둘째 줄(8번), 대화상자의 "최신 결과로 바꿨습니다"(10번), 사라진 폴더 안내(이 절의 Q17).

결과: 목록의 문구는 모두 README와 같다. 고칠 문구는 없다. 빠진 것과 더할 것은 아래와 같다.

2.3.2 "수집 실패 목록"의 "판 바뀜 안내(새 판으로 다시 열기)": 진행 중인 스캔 밖의 결과를 볼 때로 좁힌다. 진행 중인 스캔에서는 목록이 자동으로 새 결과로 넘어가므로 이 안내가 나타나지 않는다. 화면 문구는 지금 구현의 값을 쓴다: 안내 "이 문제 목록은 교체된 결과에 속합니다. 새 결과로 다시 여세요.", 단추 "새 결과로 다시 열기" / "최신 결과로 다시 열기". 와이어프레임의 "판 바뀜", "새 판"은 설계 용어이므로 화면 문구 자리에는 쓰지 않는다. 진행 중인 스캔의 목록은 새 항목 숨기기와 "지금 반영"이 탐색 표와 한 부품으로 들어올 때까지 최소 범위(한 결과의 행만, 펼침·필터·스크롤 유지)로 동작한다는 점도 적는다.

HLD와 DLD의 나눔(문서 심사 소견)에 대한 디자인팀 입장: 미루는 조건의 수치와 세부를 DLD로 옮기는 것은 괜찮다. 조건은 두 가지다. HLD에는 사용자가 겪는 원칙이 남아야 한다(값은 제자리에서 바뀐다, 누르려는 대상은 움직이지 않는다, 한 목록은 한 결과의 행만 보인다, 미뤄 둔 것이 있으면 사용자가 직접 반영할 수 있다, 화면이 스스로 옮겨 갈 때는 이유를 남는 줄로 알린다). 그리고 세부 조건(미루는 다섯 가지, 빈도, 안내를 보이는 조건, 초점과 스크롤 유지)은 발행되는 문서 어딘가에 빠짐없이 들어가야 한다. 이 README는 인계 자료이지 발행 설계가 아니다.

### 13. 키가 없는 행 (2026-11-15, 표준화팀 사전 판단에 따른 결정 요청)

전제(총괄이 전한 내용): 파일 행에도 폴더와 같은 틀의 키를 발급한다. 그래도 키가 생략되는 행이 있다(경로 길이 상한 초과, 스캔 계보가 아닌 원천, 세션 키 생성 실패). 이런 행은 새 판에서 같은 행인지 확인할 방법이 없다. 번호로 다시 찾을 수 없고 표시 이름으로 맞추는 것도 금지다. 디자인팀은 표준화팀의 판단 문서를 읽지 못했고 이 전제만 보고 정했다.

원칙: 확인할 수 없는 것을 같은 항목인 것처럼 다루지 않는다. 초점은 자리이므로 자리를 지키고, 선택과 표지는 항목에 붙는 것이므로 넘기지 않는다.

| 키 없는 행에 있던 것 | 새 판으로 넘어갈 때 |
| --- | --- |
| 초점 | 같은 자리의 행으로 간다. 같은 자리란, 위쪽에서 가장 가까운 키 있는 행(새 판에 남아 있는 것) 다음으로 같은 칸 수만큼 내려간 행이다. 그 자리에 행이 없으면 그 키 있는 행으로, 위쪽에 키 있는 행이 없으면 표의 같은 순서의 행으로, 표가 비었으면 4번과 PR #63의 규칙("위로", 제목)으로 간다. 자리에 온 행의 이름이 전과 다르면 화면 낭독기가 새 이름을 읽는다 |
| 선택 | 푼다. 키 있는 행의 선택은 남는다. 선택 동작 줄의 개수가 줄고, 줄에 한 번 알린다: "결과가 바뀌어 항목 N개의 선택이 풀렸습니다" / "The result changed, so N items were deselected". 같은 폴더를 보는 동안 이 알림은 한 번만 보인다 |
| 열려 있던 행 메뉴 | 닫는다. 초점은 위의 "초점" 규칙을 따른다 |
| 열려 있던 항목 상세 | 받은 값을 그대로 보인다(10번의 4). 더 읽어야 하는 동작("경로 복사")은 다시 읽을 수 없으므로 하지 않고 알린다: "이 항목을 최신 결과에서 다시 찾을 수 없습니다. 목록에서 다시 여세요." / "This item can't be matched in the latest result. Open it again from the list." 닫으면 초점은 "초점" 규칙을 따른다 |

같은 사실에서 따라 나오는 것:

- 미루는 동안의 숨기기(10번의 1): 키 없는 행은 숨기지 않고 항상 보인다. 새 항목인지 보던 항목인지 가릴 수 없고, 보던 행이 사라지는 쪽이 드물게 한 칸 밀리는 쪽보다 나쁘다. 3번의 안내("새 항목이 있습니다")는 키 있는 숨긴 행이 있을 때만 보인다.
- "먼저 분석": 키 없는 폴더에는 요청할 수 없다. 행 단추는 보이지 않고, 선택 동작 줄과 행 메뉴에서는 비활성이며 사유는 "이 폴더는 먼저 분석하도록 요청할 수 없습니다" / "Analyze first isn't available for this folder"다.
- 키 없는 폴더 안을 보고 있을 때: 새 판에서 그 폴더를 다시 열 수 없다. 스캔이 실행되는 동안 1초마다 상위 폴더로 튕겨 나가면 그 폴더를 볼 수 없게 되므로, 이 경우에는 자동 반영을 하지 않는다. 표는 받은 값을 보이고 선택 동작 줄에 알린다: "이 폴더는 스캔 중에 자동으로 바뀌지 않습니다 · 최신 결과는 상위 폴더에서 다시 열어 볼 수 있습니다" / "This folder doesn't update during the scan · Open it again from its parent folder to see the latest result". 같은 줄에 "상위 폴더로" / "Go to parent folder" 단추를 둔다(가장 가까운 키 있는 상위 폴더를 최신 결과로 연다). 이 표의 행 동작이 판이 바뀌어 거절되면 PR #60에서 하던 대로 알린다. 경로 길이 상한을 넘는 깊은 폴더가 여기에 해당하므로 드문 경우로만 보지 않는다.

확인이 필요한 것 (F02와 표준화팀): 키 없는 행이 실제로 얼마나 나오는지. 경로 길이 상한이 Windows의 긴 경로에서 자주 걸리는 값이면 위의 마지막 경우가 흔해지고, 그때는 상한을 올리는 쪽이 화면 규칙보다 낫다.

경로 길이 상한에 대한 답 (2026-11-15, 총괄): 키 전체의 상한은 8,192자(표준화 초안)이고, 경로의 원래 크기로는 약 6,000바이트까지 키가 나온다(UTF-8 기준, 한글 약 2,000자, 영문 약 6,000자). Windows의 일반 경로 한도 260자는 물론 긴 경로에서도 이를 넘는 일은 드물다. 스캔이 아닌 원천(샘플, 기록 등)은 자동 반영 대상이 아니고, 세션 키 생성 실패는 사실상 없다. 정확한 비율은 F02가 구현 때 잰다.

이에 따른 판단: 키 없는 행은 드문 경우다. 위 규칙은 그대로 두고 범위를 넓히지 않는다. "키 없는 폴더 안을 보고 있을 때"의 화면은 가장 단순한 형태로 구현하면 된다(안내 한 줄과 "상위 폴더로" 단추). 실측에서 흔하게 나오면 다시 정한다.

### 14. 대응표 대조 (2026-11-15, F02의 1차 대응표)

대상: docs/handoff/2026-11-15/F02-design-rule-coverage.md (F02 작성, HLD 작업 판 171, DLD 작업 판 138, 발행 전 초안).

대응표에 더할 것 (F02가 이미 알린 것 포함):

이 표의 범위 밖이지만 발행 설계에 들어가야 하는 화면 규칙 (F02가 자리를 확인한다): 탐색 패널의 초점 복원과 "위로"의 초점 유지, 표가 카드로 바뀌는 기준(PR #63), 한국어 낱말 단위 줄바꿈의 기본화(PR #63), 이름 앞뒤 공백 표시와 이름표 쌓기(PR #57), 선택 동작 줄 안의 알림과 비활성 사유(PR #45), 공용 비활성 색의 대비 기준(PR #58), 고대비 모드의 테두리 없는 단추(PR #63). 구현은 병합됐거나 검수를 마쳤지만, 규칙이 이 README에만 있으면 뒤에 바뀌어도 알 수 없다.

### 15. 설계 초안 본문 대조 (2026-11-15, AIDA 읽기 전용)

AIDA(192.168.1.201)에 읽기 전용으로 연결해 F02 기능 HLD(작업 판 172, 초안)와 기능 DLD(작업 판 141, 초안)의 본문을 직접 읽었다. 14번의 "색인 대조까지"라는 한계를 이 절로 푼다. 초안 본문은 이 문서에 옮기지 않고 자리와 소견만 적는다. F05의 HLD·DLD는 읽지 않았다.

읽은 범위: DLD의 gui-web "결과 표시의 자동 반영과 수집 실패 목록" 묶음 전체(개요, 적용·전제·방향·의존, 처리 순서 1)~11)과 9-1)·9-2), 반영기 상태, 설정 표, 오류, 시험과 검수 캡처, 화면 문단), "먼저 분석" 응답 처리표, 질문 표 Q13~Q18. HLD의 "스캔 중 자동 반영" 원칙 문단과 IF-03 주변 문단. 그 밖의 HLD 본문(와이어프레임 포함)은 문구를 문자열로 찾아 확인했다.

문구 대조: 이 README의 화면 문구 54개를 두 초안의 본문에서 찾았다. 13번(키 없는 행)의 문구 3개를 빼고 모두 HLD나 DLD에 있다. 옛 문구 "새 판으로 갱신", "새 판 있음", "판 바뀜"은 두 초안에 없다. "먼저 분석하는 중"은 IF-08 뒤에 쓴다는 주석과 결정 기록으로만 나온다.

본문이 README와 같은 뜻인 것 (확인함):

- HLD의 원칙 ①~⑤가 디자인팀이 남겨 달라고 한 다섯 가지와 같다.
- DLD 처리 순서 2)~8): 값 박자 1초, 자리 이동 박자 2초, 미루는 조건 다섯 가지와 수치, 숨긴 행의 취급, 선택·초점·스크롤 기준점, 여러 쪽, "지금 반영"이 판을 바꾸지 않는다는 점, 일시 중지와 완료.
- DLD 9)·9-2)·10)·11): 요약, 검사 문제 목록의 최소 범위, 대화상자와 "경로 복사" 이어서 하기, 사라진 폴더.
- 설정 표의 수치(1초, 2초, 1초, 2초, 200ms, 이어서 하기 1회)와 시험의 경계값.
- Q13·Q14·Q17의 결정 기록, 진행 중인 스캔 밖에서만 보이는 다시 열기 안내와 그 문구.

고칠 곳 (F02에 전달):

1. DLD "먼저 분석" 응답 처리표에 "대상 결과 판에 그 폴더가 없음"(HLD가 정한 사유 browse.location_missing)의 처리가 보이지 않는다. 표는 "범위 밖"과 "참조를 쓸 수 없음" 두 사유만 "찾을 수 없어 먼저 분석하지 못했습니다" 알림에 잇는다. 폴더가 없는 경우도 같은 알림으로 잇는다.
2. DLD 질문 표 Q15는 분리 키를 쓰므로 길이 상한이 해당 없다고 적는데, HLD는 키가 8,192자를 넘는 폴더에는 키를 발급하지 않는다고 적는다. 둘 중 하나로 맞춘다. 키 없는 행 규칙(13번)이 어느 쪽을 전제로 하는지가 여기서 갈린다.
3. DLD 시험 문단의 "대화상자 펼침 중 판 변경이면 전체 다시 읽기"는 옛 표현이다. 계기는 "경로 복사"다(같은 문단 뒤쪽과 처리 순서 10)은 이미 맞다).
4. DLD 9-1)과 설정 표의 대기 한도가 아직 1초 하나다. PR #69의 세 번째 확인대로 영역의 박자와 같게 고친다(설명 1초, 비교 2초). "다시 읽는 중…"을 보이는 조건, 일시 중지 중의 오류, 세 번 잇단 실패와 "다시 시도"도 넣는다(F02가 넣기로 한 것).
5. 13번(키 없는 행)이 DLD에 없다. HLD는 키가 없는 폴더에서 "먼저 분석"을 쓸 수 없게 둔다고 적고 세부를 DLD로 넘기는데, DLD에 사유 문구와 초점·선택 규칙이 아직 없다(F02가 넣기로 한 것).

발행 심사에 대한 디자인팀 의견: 위 1~3은 작은 수정이고 4~5는 이미 정한 내용을 옮기는 일이다. 이 다섯 가지가 들어가면 화면 동작에 관한 디자인팀의 이견은 없다. 키 계약 자체(F05 개정)는 디자인팀이 읽지 않았다.

### 16. 이미 구현된 화면 규칙의 설계 문서 자리 (2026-11-15, F02의 조사에 대한 디자인팀 판단)

대상: docs/handoff/2026-11-15/F02-design-rule-homes.md (F02 작성, 색인). 디자인팀은 이 색인을 읽었고, 색인이 가리키는 아키텍처 DLD와 F05 초안의 본문은 읽지 않았다.

F02의 조사 결과: PR #45, #57, #58, #63에서 정한 화면 규칙 12건 가운데 설계 문서에 적힌 것은 2건뿐이다(선택 동작 줄 안의 알림, 비활성 사유. 둘 다 F02 초안). 나머지는 README에만 있거나 설계 문서에 다른 내용이 있다.

자리 제안에 대한 판단: 받아들인다. 탐색 패널의 동작(초점 복원, "위로", "더 불러오기", 선택 동작 줄의 자리와 모양)은 F05 초안에, 공통 부품과 테마 토큰(카드 전환 폭, 낱말 단위 줄바꿈, 고대비의 테두리 없는 단추, 이름 공백 표시, 이름표 쌓기, 공용 비활성 색, 공통 초점 규칙)은 아키텍처 DLD에 둔다.

어긋난 두 곳의 정본:

- (가) 공용 비활성 색: 정본은 PR #58에서 정하고 병합된 값이다. 바탕은 투명, 테두리는 구분선 색, 글자는 Light #7f858e · Dark #838890, 비활성 글자의 대비는 다섯 바탕(카드, 화면, 회색 줄, 포인터 바탕, 선택된 바탕) 모두에서 3:1 이상, 비활성의 테두리 유무는 활성일 때를 따른다. 아키텍처 DLD 초안의 값(Light #e9ebef / #596575, Dark #282e36 / #a4aebc)은 이 결정보다 앞선 값이고, 회색 바탕 위에서 비활성 단추가 활성 단추와 구별되지 않던 원인이다. 아키텍처 DLD를 고친다. "불투명도 대신 전용 토큰을 쓴다"는 원칙은 그대로 맞다.
- (나) 항목 상세를 닫았는데 원래 행이 사라졌을 때의 초점: 정본은 README(PR #63)의 순서다. 같은 자리의 행 → 마지막 행 → "위로" → 제목. F05 초안의 "다음 행 → 이전 행 → 위치 폴더"를 이것으로 바꾼다. "같은 자리"가 사라진 행 바로 다음 행을 뜻하므로 F05의 "다음 행"과 첫 단계는 같다. 달라지는 것은 뒤쪽이다. 표가 비었을 때 큰 영역(위치 폴더 패널)에 초점을 두지 않고 "위로" 단추나 제목으로 보낸다.

조건: 이 규칙들이 발행 설계에 들어갈 때까지 README가 유일한 기록이다. 아키텍처 DLD의 담당이 정해지면 디자인팀이 그 초안의 해당 절을 AIDA에서 직접 읽고 대조한다.

### 17. 공통 화면 규칙을 아키텍처 DLD에 넣음 (2026-11-15, 총괄 배정)

16번에서 아키텍처 DLD에 두기로 한 규칙을 디자인팀이 직접 넣었다. 자리는 아키텍처 DLD 2.2.3 「화면 모듈 구조와 IPC 클라이언트」의 "사용자 화면·상호작용" 칸이다. 작업 판 1478에서 1479가 됐고 발행 전 초안이다. 발행과 개정 취소는 하지 않았다.

넣은 것:

1. 토큰 표의 비활성 행을 PR #58 값으로 바꿨다(표면 투명, 경계는 장식 경계 토큰, 글자 Light #7f858e · Dark #838890).
2. 「공통 부품 대응과 역할」 표의 "수치와 근거" 행에 NameText를 더하고, 이 행과 "표·그래프" 행이 새 표를 가리키게 했다.
3. "OS 색 구성…" 문단에 비활성 규칙을 더했다. 다섯 표면에서 3:1 이상과 시험 고정, 활성일 때 경계가 없는 조용한 동작은 비활성일 때도 경계가 없다는 것, 강제 색상 모드에서 GrayText와 1 CSS px 경계.
4. 새 표 「공통 표시·배치 규칙」 다섯 행: 표와 카드의 전환(표 영역 700 CSS px 미만), 줄바꿈, 한 덩어리로 두는 값, 이름의 앞뒤 공백 표시(U+2423), 이름표와 값의 배치.
5. 새 표 「공통 초점 규칙」 다섯 행과, 탐색 패널의 풀이는 F05가 맡는다는 문단.

짜임은 구현 문구를 따른다. 누른 뒤 "비교 범위"에 나오는 값("이 볼륨에서 … 모든 폴더")과 같은 말이어야 누른 것과 나온 것이 이어진다.

낱말은 "스캔"이다. 한국어 화면이 같은 동작을 "스캔 시작", "스캔 중", "스캔 완료"와 "검사 대상", "검사 문제", "검사한 폴더"로 섞어 부른다. 영어는 모두 scan이다. "검사"는 무결성 검사, 중복 검사, 항목 검사(Inspect)에도 쓰이므로, "스캔 시작"을 누른 사람이 결과에서 "검사 문제"를 보면 다른 검사가 따로 돌았다고 읽을 수 있다.

디자인팀 결정: 사용자에게 보이는 말은 "스캔" 하나로 한다. "검사"는 무결성·유효성·중복 검사와 Inspect에만 남긴다.

바꿀 대상(0.0.1 dda8a23e의 ko.json, 값만 바꾸고 키와 영어는 그대로): ui.analysis.choose_path_or_reopen, reopen_saved_or_select, scan_targets, scan_and_results, issues_region, issues_hide, issues_view, issues_explanation, issues_reading, issues_none, issue_entries, issues_retry, issues_failed, volume_factor_out_of_scope, volume_scan_unavailable, volume_target_outside_scan, volume_response_mismatch, volume_scanned_folder, volume_all_scanned_folders, volume_selected_folder, volume_used_end, volume_scanned_allocation, volume_compare_all. 모두 23개다.

상태 (2026-11-15, 총괄 채택): F02가 소형 PR로 23개 값을 바꾼다. 문구 표는 F02에 보냈다. 병합될 때까지 구현 화면에는 "검사"가 남는다. 이 README의 다른 절이 그때의 구현 문구로 적은 "검사 문제 목록"은 기록으로 두고, 병합 뒤에는 "스캔 문제 목록"으로 읽는다. PR #73은 병합됐다. 용어의 기준은 design/TERMS.md다(사용자 결정으로 AIDA 용어 사전은 쓰지 않는다).

### 21. F05 초안의 화면 동작 절 대조 (2026-11-15, HLD 작업 판 124, DLD 작업 판 104, 발행 전)

16번에서 F05 몫으로 정한 규칙과 13번(키 없는 행), Q17(사라진 폴더)이 F05 초안에 들어갔다고 F02가 알려 와 AIDA에서 직접 읽었다. 본문은 옮기지 않는다.

결과: README와 같은 뜻이다. 화면 동작에 관한 이견은 없다. 초점 복원 순서는 "같은 자리의 행 → 마지막 행 → 위로 → 제목"으로 고쳐져 있다.

13번에 없어 초안이 채운 다섯 가지에 대한 판단:

1. 위치 없이 다시 열 수 있는 범위 루트와 가상 최상위는 "키 없는 폴더 안"으로 보지 않는다. 동의.
2. 키 있는 상위가 하나도 없으면 "상위 폴더로"는 범위 루트를 연다. 동의.
3. 맨 위에 보이던 행에 키가 없으면 그 아래의 보이는 키 있는 행을 스크롤 기준으로 쓰고, 없으면 스크롤 위치를 그대로 둔다. 동의.
4. 키 없는 폴더 행의 펼침은 새 결과에서 접는다. 동의하되 규칙 하나를 더한다. 스캔이 진행 중인 결과에서 키 없는 폴더 행은 그 자리에서 펼칠 수 없다. 펼침 표지는 비활성이고 사유는 "스캔 중에는 이 폴더를 펼칠 수 없습니다 · 폴더를 열면 안을 볼 수 있습니다" / "This folder can't be expanded during the scan · Open the folder to see inside"다. 펼친 가지가 1~2초 뒤 접히고 다시 펼치면 또 접히는 일을 막는다. 접는 규칙은 안전망으로 남는다.
5. 초점의 같은 순서 자리에 행이 없으면 마지막 행으로 간다. 동의.

F05 초안에서 고칠 곳(F02에 전달): 위 4번의 추가 규칙과 문구, 사라진 폴더로 옮길 때 열려 있던 항목 상세의 처리(받은 값을 보이고 닫으면 옮겨 간 폴더 표의 첫 행), 키 없는 폴더의 "먼저 분석" 사유 영어(F02 항목을 가리키게), "아키텍처 DLD 2.2.3(디자인팀 개정 예정)"을 저장된 「공통 초점 규칙」 표로 바꾸기.

정본 나누기(F02의 제안에 동의): 탐색 표의 행, 초점, 선택, 펼침, 스크롤, 사라진 폴더, 키 없는 행은 F05가 정본이다. 반영을 미루는 조건과 "새 항목이 있습니다", "지금 반영", "먼저 분석"의 사유와 알림은 F02가 정본이다. 이 README의 13번은 두 문서가 함께 옮겨 적은 원문이고, 발행 뒤에는 두 문서의 해당 항목이 기준이다.

읽은 범위: DLD 2.2.1 전체, 2.2.2의 초점 복원·키 배정·경로 복사 문단과 표, 2.2.5 표, 3.1 Q16. HLD 2.2.3의 키 문단과 "한 목록은 한 판", 2.3.1의 초점 복원 표와 검증 행, 2.3.2의 실패 표·정책 문단·검증 경로·화면 규칙 표, 2.3.3의 선택 동작 줄 문단, 3.1 Q8.

F02 HLD 182판과 DLD 157판(13번 규칙을 F05 참조로 줄인 판)은 읽지 않았다.

### 22. "먼저 분석"을 엔진 문제로 처리하지 못했을 때 (2026-11-15, F02 DLD Q21의 답)

표준화 결정으로 생긴 새 실패다. 문구는 "문제가 생겨 ‘영상’ 폴더를 먼저 분석하지 못했습니다 · 스캔은 그대로 계속됩니다" / "Something went wrong, so ‘Videos’ wasn't analyzed first · The scan continues as before"다.

- 선택 동작 줄의 문구 자리에 다른 "먼저 분석" 알림과 같은 표시 시간 동안 보이고 상태 영역으로 한 번 알린다.
- 그 행에 "먼저 분석 요청됨" 표지를 달지 않는다. 다른 폴더에 달려 있던 표지는 그대로 둔다. "먼저 분석" 단추는 활성으로 남아 다시 누를 수 있고, 초점은 단추에 남는다.
- 무엇이 안 됐는지와 스캔이 계속된다는 것을 한 줄에 함께 쓴다. 사용자가 먼저 걱정하는 것은 스캔이 깨졌는지다.
- 전제(F02가 코드로 확인): 이 실패는 요청을 검사하는 단계에서 나오고, 검사가 모두 끝난 뒤에야 우선 영역이 바뀐다. 그래서 실패 뒤에도 스캔 순서와 이전 우선 영역이 그대로다. F02가 초안에 규칙과 시험으로 넣는다. 구현에서 이 시험이 실패하는 경우가 나오면 뒤 구절을 뺀다. 스캔 자체가 실패로 끝났으면 이 알림을 띄우지 않는다.

용어: "분석"은 사용자가 시작하는 일 전체와 그 결과, "스캔"은 그 안에서 파일 정보를 읽어 들이는 과정으로 구분해 쓴다. 기준은 design/TERMS.md에 적었다(사용자 결정으로 AIDA 용어 사전은 쓰지 않는다).

### 23. "분석"과 "스캔"의 구분 (2026-11-15, 용어 정리 2차)

F02가 용어 사전 등록안을 만들다가 물었다. "분석"이 사용자가 시작하는 일 전체라면 "스캔 시작" 단추는 "분석 시작"이 맞지 않느냐는 것이다. PR #73 머리(5bfe080e)의 문구 묶음을 모두 확인했다. 한국어 문구에서 "분석"은 54개, "스캔"은 79개이고 대부분은 아래 구분대로다. 어긋난 곳은 분석을 시작하는 흐름과 "범위"에 붙는 말 20개다. 한 화면에 제목 "분석 대상과 범위"와 단추 "스캔 범위 검토", "스캔 시작"이 함께 있고, 결과 화면에서는 같은 동작이 "다시 분석"이다. 설정에는 같은 설정이 "최근 분석 범위 기억"과 "최근 스캔 범위 기억" 두 이름으로 있다. 영어도 같은 자리에서 섞여 있다.

디자인팀 결정:

- 분석: 사용자가 시작하고 결과를 얻는 일. 시작, 다시 하기, 대상, 범위, 결과에 쓴다(분석 시작, 다시 분석, 분석 대상, 분석 범위, 분석 결과, 먼저 분석).
- 스캔: 분석 안에서 파일 정보를 읽어 들이는 실행. 진행 상태와 그 제어, 그 실행이 남긴 것에 쓴다(스캔 중, 스캔 일시 중지, 스캔 계속, 스캔 취소, 스캔 완료, 스캔 문제, 스캔한 폴더, 스캔 기록).
- 예외는 두지 않는다. "분석 시작"을 누르면 상태 표지는 "스캔 중"이다.

### 24. 분석을 시작한 뒤의 초점과 스캔 중의 합계 (2026-11-15, PR #82 캡처에서 본 것)

PR #82는 일곱 문구를 더한 머리(e3c9593e)까지 디자인 동의다.

분석을 시작한 뒤의 초점: 지금 구현은 "분석 시작"을 누르면 초점을 결과 머리의 상태 표지("스캔 중")로 옮기고 테두리를 그린다(2026-11-11에 들어온 동작으로, 공통 초점 규칙보다 먼저 만들어졌다). 다음으로 바꾼다.

- 초점은 화면 제목("디스크 공간 분석 결과")으로 보내고 테두리를 그리지 않는다. 분석을 시작하면 화면이 결과 화면으로 바뀌므로 공통 초점 규칙의 "화면에 들어옴"에 해당한다. 결과 화면 안의 편집기에서 다시 시작한 경우에도 같다.
- 상태 표지에는 초점을 두지 않는다. "스캔 중"은 상태 영역으로 한 번 알린다.
- "스캔 일시 중지" 단추로 보내지 않는다. "분석 시작"을 Enter로 누른 사람이 한 번 더 누르면 시작하자마자 스캔이 멈춘다.
- 스캔이 끝나거나 취소돼 초점이 있던 "스캔 일시 중지"나 "스캔 취소"가 사라질 때는 같은 줄에 남는 "폴더 탐색"으로 보내고, 없으면 제목이다. 초점이 그 단추들에 없었으면 옮기지 않는다.
- F02가 space-format 결함 PR에 함께 넣는다. 검수는 시작 직후 캡처 한 장이다.

스캔 중의 합계: PR #82의 캡처(시작 1.1초 뒤, 파일 15만 개가 든 큰 폴더 하나)에서 할당 크기가 가장 큰 글자로 "확인 불가 · 일부만 측정됨"이었다. PR #69의 녹화(폴더가 여러 개인 자료)에서는 0.6초부터 값이 자랐다. 큰 폴더 하나를 읽는 동안 얼마나 이어지는지는 아직 모른다. F02가 같은 자료로 녹화해 확인한다. 디자인 기준: 스캔 중의 합계는 지금까지 확인한 만큼을 최소값으로 보인다. 엔진이 값을 줄 수 없는 구간이 있으면 "확인 불가"가 아닌 진행 중임을 알리는 표시를 쓴다. 가장 큰 글자가 "확인 불가"로 몇 초 넘게 떠 있으면 실패로 읽힌다. 녹화를 보고 고칠 방법을 정한다.
### 25. 선택이 스스로 풀릴 때의 알림 (2026-11-15, 탐색 표와 그래프 공통)

진행 중인 스캔의 새 결과를 반영할 때 선택이 사용자가 한 일 없이 풀리는 경우는 둘이다. 둘 다 한 번 알린다. 목록과 그래프가 같은 선택을 쓰므로 같은 일에는 같은 문구 키를 쓴다.

| 경우 | 한국어 | 영어 |
| --- | --- | --- |
| 고른 항목이 새 결과에 없음 (키 있는 행이나 도형이 사라짐) | 항목 N개가 최신 결과에 없어 선택이 풀렸습니다 | N items are no longer in the latest result, so they were deselected |
| 키 없는 행이나 도형의 선택이 풀림 | 결과가 바뀌어 항목 N개의 선택이 풀렸습니다 | The result changed, so N items were deselected |

- 두 문장을 나누는 이유: 앞의 것은 그 항목이 이제 없다는 뜻이고, 뒤의 것은 다시 고르면 된다는 뜻이다.
- 같은 판 변경에서 두 경우가 함께 생기면 뒤 문장 하나로 합치고 N은 더한 수다. 두 줄을 잇달아 보이지 않는다.
- 키 없는 행의 알림은 같은 폴더를 보는 동안 한 번이다(13번). 키 있는 행이 사라진 알림과 합쳐진 알림은 생길 때마다 보인다. 같은 스캔 안에서는 키 있는 행이 사라지지 않으므로 드문 일이다.
- 자리는 선택 동작 줄의 문구 자리다. 다른 알림과 같은 표시 시간 동안 보이고 원래 문구로 돌아간다. 상태 영역에는 선택이 풀린 일 하나에 한 번만 알린다(표와 그래프가 함께 보여도 한 번). 알림은 선택 상태의 소유자인 탐색 기능이 내고, 표와 그래프와 대체 표는 자기 자리에 문구만 보인다. N은 그 판 변경에서 풀린 선택 항목의 수이고 같은 항목은 한 번만 센다.
- 스캔이 끝나 선택 동작 줄이 없을 때(최종 결과를 반영하면서 풀린 경우)는 표 위의 안내 띠에 보인다. 사라진 폴더 안내와 같은 자리 규칙이다. 띠는 표시 시간으로 지우지 않고, 사용자가 닫거나 행을 새로 고르거나 다른 폴더로 가면 없어진다. 스캔이 끝나는 순간에는 사용자가 화면을 보고 있지 않을 수 있기 때문이다. 상태 영역에는 한 번 알린다(F05 DLD Q18의 답). 읽는 순서는 탐색 알림 영역의 우선순위(거절, 사라짐, 갱신, 완료)에서 "사라짐"으로 다룬다. 사용자가 하려던 일에 영향을 주는 것부터 읽는 순서다. 처음에는 "스캔 완료 다음에 읽는다"고 답했다가 이 순서가 이미 있어 거두었다(F05 DLD Q20의 답). 스캔 완료를 다른 영역이 알리는 경우 두 영역 사이의 순서는 따로 맞추지 않는다.
- 보던 폴더가 사라져 상위 폴더로 옮겨 가는 경우에는 이 알림을 띄우지 않는다. 사라진 폴더 안내 줄이 이유를 말한다.
- 진행 중인 스캔이 아닌 판 변경(재대응 경로)은 "이전 선택 표지"로 처리하고 이 문구를 쓰지 않는다.
- 영어의 단수는 문구 체계가 수에 따른 꼴을 지원하면 자연스러운 단수 문장으로, 아니면 "No longer in the latest result. Items deselected: N" / "The result changed. Items deselected: N"으로 쓴다. F02가 구현할 때 정한다.

이 절은 4번과 10번의 "사라지면 풀림"에 알림을 더한 것이다. F02가 F05 초안(DLD 2.2.1.5의 위치 유지 규칙 표, 2.2.1.4 5), 시험, HLD 2.3.2.13)에 넣는다.

기록: 이 절의 알림은 F05 초안 HLD 작업 판 139, DLD 작업 판 119에 들어갔다(F02가 알림, 디자인팀은 다시 읽지 않음). F02 초안은 HLD 작업 판 185, DLD 작업 판 163이다(Q21을 응답 처리표와 문구 표에 넣고 닫음). F05 초안은 HLD 작업 판 136, DLD 작업 판 115다(화면 동작 문장은 131판·110판과 같다고 F02가 알림). 디자인팀은 이 판들을 다시 읽지 않았다.
### 26. 스캔 시작 직후의 "확인 불가"와 그 밖의 결함 (2026-11-15, F02의 측정과 캡처)

24번에서 물은 것의 답이다. F02가 VM에서 화면의 값을 0.2초마다 읽어 쟀다(큰 폴더 하나에 파일 15만 개, 폴더 150개에 파일 1,000개씩, 큰 폴더를 대상으로 직접 고른 경우).

사실: "확인 불가 · 일부만 측정됨"은 첫 결과가 게시된 때부터 다음 게시까지 약 1초만 나온다. 그 뒤로는 "최소 390.7 KiB", "최소 1.1 MiB"처럼 1초마다 자란다. "확인한 항목" 수는 그동안에도 계속 는다. 원인은 첫 결과에 크기를 가진 파일이 아직 하나도 없으면 합계가 알 수 없음이 되기 때문이다. 요약의 자동 반영은 제대로 동작한다.

고칠 것(화면에서 고친다): "확인 불가"는 알아낼 수 없다는 뜻인데 이때의 사실은 아직 없다는 것이다.

- 조건: 화면이 보고 있는 스캔이 실행 중이고, 요약의 크기 값이 알 수 없음이며, 그 값에 측정 제한 사유가 붙어 있지 않을 때.
- 표시: 큰 글자 자리에 "계산 중…" / "Calculating…", 아랫줄에 "스캔하는 대로 값이 나타납니다" / "The value appears as the scan runs". 큰 글자는 값과 같은 크기와 자리이되 보조 글자색이다. 도는 표시는 넣지 않는다. 줄 높이는 그대로다.
- 일시 중지 중에 같은 조건이면 "아직 값이 없습니다" / "No value yet", 아랫줄 "스캔을 계속하면 나타납니다" / "It appears when the scan continues".
- 스캔이 끝난 뒤의 알 수 없음과, 사유가 붙은 알 수 없음은 지금처럼 "확인 불가"와 사유다. 끝까지 나오지 않을 값에 "계산 중…"을 쓰지 않는다.
- 첫 게시의 알 수 없음에 사유가 붙어 오면 이 조건으로 가릴 수 없다. 그때는 할당 크기와 논리 크기에만 적용한다(F02 확인 대기).
- "측정 상세" 안의 같은 값에도 같은 규칙을 쓴다.

스캔이 끝난 직후의 틈: 표지가 "스캔 완료"로 바뀐 뒤 약 0.4초 동안 값은 "최소 8.4 MiB · 일부만 측정됨"이고 둘째 줄이 "결과 판: 중간 결과"다. 결과가 크면 더 길어진다. 스캔이 끝났는데 최종 결과가 0.3초 안에 오지 않으면 둘째 줄을 "최종 결과를 읽는 중…" / "Reading the final result…"으로 바꾸고, 최종 결과가 오면 값과 "결과 판: 최종"을 함께 바꾼다. 0.3초 안에 오면 바로 바꾼다. 후속으로 둬도 된다.

F02가 고친 것(캡처로 확인, 디자인 동의):

- 측정 사유가 한국어 화면에 영어로 나오던 결함. "측정 상세"의 사유 네 가지가 한국어로 한 줄씩 나온다(1b 캡처). 폴더 상세의 "파일 시스템이 알려 준 값"도 함께 고쳤다고 한다(그 캡처는 보지 않았다).
- 분석을 시작한 뒤의 초점(24번). 시작 0.8초 뒤 표지에 테두리가 없고 초점은 제목이다(2 캡처와 접근성 읽기). 끝나거나 취소될 때의 세 경우는 시험으로만 확인했다고 한다. 실제 화면 낭독기로 들은 적은 없다.

남은 것:

- 사유 space.hardlink_identity_unknown에 문구가 없어 일반 문구로 나온다. 뜻을 F02가 확인하면 정한다. 겹쳐 세는 일과 이어진 뜻이면 "이름이 여러 개인 파일을 가려낼 수 없어 크기가 겹쳐 세어졌을 수 있습니다." / "Files with more than one name could not be told apart, so some sizes may be counted more than once."
- 폴더 상세의 "종류" 값이 directory 그대로 나오고 "진단 사유"가 사유 키를 그대로 보인다. 내부 값이 사용자에게 보이는 결함이다. F02가 값 목록을 보내면 디자인팀이 문구 표를 쓴다.
PR #85 검수 (2026-11-15, 초안): 디자인 동의, 조건 넷. 캡처 두 장을 봤다(시작 0.6초 뒤의 "계산 중…", 완료 0.4초 뒤의 "최종 결과를 읽는 중…"). Dark와 "측정 상세"를 펼친 화면, 일시 중지 중의 화면은 보지 않았다.

구현에서 확인된 사실과 그에 따른 규칙:

- 첫 게시의 알 수 없음에는 항상 사유가 붙어 온다. 그래서 "사유가 없을 때"라는 조건은 쓸 수 없고, 논리 크기와 할당 크기에만 사유와 무관하게 적용한다. 중복 없는 실제 크기는 스캔 중에도 "확인 불가"다.
- 사유에 파일 식별 한도 초과나 집계 넘침이 있으면 스캔 중에도 "확인 불가"다(F02가 더한 예외, 동의). 이 두 경우는 엔진이 스캔 끝까지 값을 내지 않는다.
- 논리 크기와 할당 크기 가운데 한쪽에 값이 생겼는데 다른 쪽이 여전히 알 수 없음이면 그쪽은 "확인 불가"로 바꾼다. 둘 다 값이 없는 채로 결과가 세 번 게시되면 둘 다 "확인 불가"로 바꾼다. 파일 시스템이 할당 크기를 알려 주지 않는 경우에 "계산 중…"이 스캔 끝까지 남는 것을 막는다.
- "측정 상세" 안에서는 "계산 중…"인 동안 그 값의 사유 줄을 숨긴다. "계산 중…"은 여기서도 보조 글자색이다.
- 값 아랫줄은 "파일 크기를 확인하는 중입니다" / "Checking file sizes"로 바꾼다. 머리의 "스캔하는 대로 값이 바뀝니다"와 겹치지 않게 하려는 것이다.
- 완료 직후에는 "결과 판: 중간 결과"를 남기고 그 아랫줄에 "최종 결과를 읽는 중…"을 쓴다(구현이 이렇게 했고 받아들였다).
- "일시 중지 요청됨"은 실행 중으로, "취소 요청됨"은 끝난 것으로 다룬다.

정한 문구:

| 자리 | 한국어 | 영어 |
| --- | --- | --- |
| 사유 space.hardlink_identity_unknown | 식별할 수 없는 파일의 할당 크기는 합계에 넣지 않았습니다. | The allocated size of files that could not be identified was left out of the total. |
| 상세의 "종류": directory, file, untraversed_link | 폴더, 파일, 따라가지 않은 링크 | Folder, File, Link (not followed) |
| "진단 사유"의 ref.unavailable | 이 결과에 값이 없습니다 | Not included in this result |
| "진단 사유"의 문구 없는 키 | 알 수 없는 사유 (키) | Unknown reason (key) |
| 요약의 단위 체계 IEC, SI | 이진 단위(KiB, MiB), 십진 단위(kB, MB) | Binary units (KiB, MiB), Decimal units (kB, MB) |
| 볼륨 값이 없을 때 space.volume_report_unavailable | 운영 체제가 볼륨 사용량을 알려 주지 않았습니다. | The operating system did not report the volume usage. |

"진단 사유"의 한 줄은 "필드 이름: 사유 문장"이다. 내부 값을 그대로 보여도 되는 곳은 "진단 사유"의 문구 없는 키뿐이다. 그 밖에 모르는 값이 오면 "알 수 없음" / "Unknown"으로 보인다. hardlink_identity_unknown의 뜻은 겹쳐 세는 것이 아닌 합계에서 빠지는 것이다(F02 확인).
아키텍처 DLD의 "화면 용어" 행 (2026-11-15): 총괄 승인으로 2.2.3의 표 「공통 표시·배치 규칙」에 행 하나를 더했다. 작업 판 1494, 발행 전. 사용자에게 보이는 말은 화면 용어 기준(TERMS.md)을 따른다는 것, 분석·스캔·검사의 구분, 같은 상태와 동작은 같은 말, 내부 값을 그대로 보이지 않는다는 것을 적었다. 저장 응답이 정상이었고 다시 읽어 블록별로 같음을 확인했다. 표준화팀이 이 저장 전 판(1493)으로 돌린 발행 점검은 통과였다(발행을 막는 항목과 사람이 처리할 항목 0건). 2.2.3에 걸린 경고는 gui-web 절의 "단위 심사가 낡음"뿐이다. 단위 심사(2026-11-15, F06 초안이 멈춘 뒤 요청): 디자인팀 저장분의 단위는 gui-web 절 전체다. 결과는 통과이고 blocker는 0건이다. major 두 건은 모두 기존 본문에 대한 것이다. 하나는 절의 필수 소절이 충분히 작성되지 않았고 "외부 연동 상세"와 "저장소 상세"가 제목만 있다는 것, 다른 하나는 "화면 모듈 구조와 IPC 클라이언트" 묶음이 모듈별 책임과 의존 방향, 그것을 강제하는 검사를 정하지 않았다는 것이다. 디자인팀이 넣은 내용(공통 표시·배치 규칙, 공통 초점 규칙, 토큰 표, 비활성 규칙, 화면 용어)에 대한 소견은 없다. 판 번호를 바꾸지 않으려고 고치지 않았고, 다음 개정에서 다룬다. 표준화팀의 세 단위도 통과했다.
### 27. 탐색 표의 "사용 가능 여부" 열 (2026-11-15)

F06의 캡처에서 이 열이 모든 행에서 "알 수 없음"인 것을 봤다. F02가 코드로 확인한 사실: 이 열은 "안을 읽지 못한 폴더"와 "제외된 폴더"를 보이려는 열인데, 엔진이 두 표지를 항상 알 수 없음으로 보낸다. 계약에 자리는 있고 채우는 구현이 없다. 그래서 어떤 결과를 열어도 모든 행이 "알 수 없음"이다.

결정:

- 엔진이 값을 낼 때까지 열을 두지 않는다. 줄마다 반복되는 "알 수 없음"은 정보가 없고 잘못된 것처럼 읽힌다. 조건을 따져 숨기는 방식은 쓰지 않는다(스크롤 중에 열이 나타났다 사라질 수 있다). F02가 탐색 화면을 만지는 다음 PR에 넣는다.
- 숨기는 것으로 끝내지 않는다. 어느 폴더의 크기가 덜 세어진 것인지 표에서 알 수 있어야 한다. 지금은 스캔 문제 목록에서만 볼 수 있다. 값을 채우는 계약("폴더 행의 수집 상태", F03·F05)의 일정을 총괄에 요청했다.

값이 생겼을 때의 모양:

- 열 이름은 "스캔 상태" / "Scan status"다.
- 안을 읽지 못한 폴더는 "안을 읽지 못함" / "Contents not read", 제외 규칙으로 빠진 폴더는 "제외됨" / "Excluded", 둘 다이면 가운뎃점으로 잇는다. 문제가 없는 행은 빈칸이다. 값을 모르는 행만 "알 수 없음"이다.
- "안을 읽지 못함"인 행은 크기 칸에 "최소 …"가 함께 보여야 한다.
- 표지가 있는 행에서 스캔 문제 목록의 해당 줄로 갈 수 있으면 좋다(행 메뉴).

PR #90은 영어 "Inaccessible locations"·"Unread locations"와 항목 상세 출처 "분석 결과"를 더한 머리(d46cda4f)까지 디자인 동의다. 더한 부분은 F02가 알려 준 내용으로 받아들였다.
수집 상태의 값 (2026-11-15, F02가 F03과 필드를 맞추다 확인한 사실에 대한 결정): 수집기는 제외 규칙에 걸린 항목을 기록하지 않는다. 그래서 제외된 폴더는 결과에 항목으로 없고 표에 "제외됨" 행이 나올 수 없다. 위의 "제외됨"은 다음으로 바꾼다.

- 부모 폴더에 제외 사실을 남긴다(F02의 수집기 변경과 빌드 API). 표에는 그 부모 행에 "제외된 항목 {n}개" / "{n} excluded items"로 보이고, 여부만 알면 "제외된 항목 있음" / "Has excluded items"다. 제외된 것이 있는 폴더의 크기는 그만큼 작게 보이는데 지금은 결과 어디에도 흔적이 없다. 크기 칸에는 "최소 …"를 붙이지 않는다(사용자가 정한 범위다).
- 제외한 폴더를 줄로 남기는 것은 0.1에서 하지 않는다. 위 방법이 0.1에 들어가지 못하면 내지 않되 구현 공백으로 적는다.

"안을 읽지 못함"에는 실패만 넣는다.

| 수집기가 들어가지 않은 경우 | 표의 값 | 크기 칸 |
| --- | --- | --- |
| 열기·읽기 실패(접근 거부 등), 판정할 수 없는 경계, 취소·연결 끊김 뒤에 만난 폴더 | 안을 읽지 못함 / Contents not read | 최소 … |
| 다른 볼륨·마운트 지점 | 다른 볼륨 / Other volume | 그대로 |
| 이미 다른 경로로 수집한 폴더 | 다른 경로에서 이미 셈 / Counted at another path | 그대로 |
| 스캔 중에 아직 차례가 오지 않은 폴더 | 빈칸 | 그대로 |

실패가 아닌 것이 실패처럼 보이면 사용자가 권한을 고치려 하거나 결과를 믿지 않게 된다. 왜 못 읽었는지는 표에 쓰지 않고 스캔 문제 목록과 항목 상세에서 본다. 둘 이상이 해당하면 가운뎃점으로 잇는다.

0.1의 범위 (총괄 확정, 2026-11-15): F02의 추정을 받아 0.1 목표를 제외 개수까지로 확정했다. 순서는 F03의 빌드 API와 폴더별 조회(2026-11-16 초안 목표), 표준화팀의 계약 PR(행의 경계 종류와 읽지 못함의 좁힌 정의, 열린 위치의 제외 개수), F02의 수집기 제외 계수, 엔진 연결, 화면("스캔 상태" 열과 머리 줄의 "제외된 항목 n개")이다. 결과 요약의 "제외 규칙 적용됨"과 경계 표시·"안을 읽지 못함"은 수집기 변경 없이 가능해 F03 조회가 나오는 대로 먼저 낸다. F03 API가 2026-11-17까지 들어오지 않으면 제외 개수는 구현 공백으로 적고 나머지 둘만 0.1에 넣는다. F05 설계 문서와 아키텍처 DLD의 탐색 행 문장은 발행 뒤 새 개정에서 고친다(F02·표준화팀). 화면이 나오면 디자인팀이 캡처로 검수한다.
제외 개수를 보이는 자리 (2026-11-15, 표준화팀 계약안에 대한 답): 계약안의 제외 개수는 "그 폴더 바로 아래에서 제외된 항목 수"(정확한 수 또는 하한)다. 이에 맞춰 위의 "부모 행에 제외된 항목 n개"를 다음으로 바꾼다.

- 0.1에서는 열려 있는 폴더에만 보인다. 자리는 탐색 머리의 요약 줄에서 항목 수 바로 뒤다: "현재 분석 · 2026-11-15 · 항목 10개 · 제외된 항목 3개". 자식 폴더 행에는 보이지 않는다.
- 바로 아래만 센 값이 정확히 답하는 물음은 "이 목록에 왜 그 항목이 안 보이는가"다. 같은 값을 자식 행에 달면 잘못 읽힌다. 제외 규칙은 대개 깊은 곳의 폴더에 걸리므로 그 상위 행에는 표지가 붙지 않고, 표지가 없는 행은 "빠진 것이 없다"로 읽힌다.
- 문구: "제외된 항목 {n}개" / "{n} excluded items", 하한이면 "제외된 항목 최소 {n}개" / "At least {n} excluded items". 0이거나 값이 없으면 쓰지 않는다. 설명은 "제외 규칙에 걸려 이 폴더에서 분석하지 않은 항목입니다. 크기와 항목 수에 들어 있지 않습니다" / "Items in this folder that were skipped by an exclusion rule. They aren't included in the size or the item count."
- 행에서 "이 폴더의 크기에 빠진 것이 있다"를 보이는 표지는 하위 전체를 본 값이 필요하므로 0.1 이후의 후속이다. 그래프의 범위 머리에도 같은 줄을 둔다(후속).

계약 값과 화면의 대응 (2026-11-19, #95·#96·#99·#100 병합 뒤 F02의 F05 개정 초안 질의에 대한 답): 위의 「스캔 상태」 열과 머리 줄 제외 수를 그대로 쓴다. 0.0.1 5f72bf3a의 탐색 화면은 두 값을 아직 쓰지 않는다.

- 경계: 생산자가 폴더 경계를 낸 응답에서만 열을 둔다. 필드가 아예 없는 응답(이전 생산자)에는 열을 두지 않는다. 경계가 없다고 확인된 행은 빈칸, 값을 모르는 행은 「알 수 없음」이다. 둘을 같은 빈칸으로 그리지 않는다. 종류별 문구와 크기 칸의 「최소 …」는 위 표 그대로다.
- 취소: 그 폴더에 대한 근거가 있을 때만 「안을 읽지 못함」이다. 결과가 취소됐다는 사실만으로 행에 붙이지 않는다.
- 제외 하위 수: 정확한 값은 「제외된 항목 {n}개」, 하한은 「제외된 항목 최소 {n}개」. 필드 생략·null·0이면 쓰지 않는다. 쓰지 않는 것이 「제외 없음」을 뜻하지는 않으며, 규칙이 있었다는 사실은 결과 요약의 「제외 규칙」 줄이 알린다.
- 행·머리 줄의 값은 그 표가 보이는 결과 판의 것이다. 다른 판의 늦은 응답으로 채우지 않는다.

### 28. 결과 요약의 제외 항목과 취소로 읽지 못한 폴더 (2026-11-15, F02의 질문에 대한 답)

제외 항목(0.1 필수): 결과 자체는 적용된 제외 규칙을 싣지 않는다. 이 창에서 시작한 분석은 화면이 범위 초안을 알고 있어 보일 수 있다.

- 결과 요약의 "스캔한 경로" 줄 바로 아래에 "제외 항목" 줄을 둔다. 값은 규칙 목록이다. 따로 "제외 규칙이 적용됨"이라는 문장은 두지 않는다. 이름표의 설명은 "분석하지 않은 항목입니다. 크기와 항목 수에 들어 있지 않습니다" / "These weren't analyzed. They aren't included in the size or the item count."

- 규칙이 없는 것이 확인되면 줄을 두지 않는다. 범위 초안을 모르는 결과는 줄을 빼지 않고 "제외 항목: 확인 불가"로 보인다. 줄이 없으면 제외한 것이 없다고 읽히기 때문이다. 설명은 "이 결과를 만든 분석 범위를 지금 확인할 수 없습니다" / "The scope used for this result isn't available now."

취소로 읽지 못한 폴더: 취소 때문에 열지 못한 폴더는 스캔 문제 목록에 폴더별 행으로 남기지 않는다(수십만 개가 될 수 있다). 탐색 표의 그 폴더 행에는 "안을 읽지 못함"이 붙고 크기는 "최소 …"다.

- 스캔 문제 목록 위에 안내 줄을 둔다: "스캔을 취소해 읽지 못한 폴더 N개는 이 목록에 하나씩 나오지 않습니다. 폴더 탐색에서 「안을 읽지 못함」으로 보입니다." / "N folders weren't read because the scan was cancelled. They aren't listed here one by one. In the folder view they are marked Contents not read." 이 줄이 없으면 목록은 0건인데 표에는 표지가 보이는 어긋남이 생긴다.
- 문제 수 표시에는 이 수를 더하지 않는다. 문제 수는 목록의 행 수와 같아야 한다.

### 30. "사용 가능 여부" 열을 뺄 때 "먼저 분석" 표지와 행 단추의 자리 (2026-11-15 저녁, F02의 질문에 대한 결정)

그 열에는 값 말고도 요청한 폴더의 "먼저 분석 요청됨" 표지와, 포인터나 초점이 간 행의 "먼저 분석" 행 단추가 들어 있다(PR #45에서 승인한 동작). 열을 빼면서 이 둘은 이름 칸 끝으로 옮긴다(F02의 A안). PR #45 검수의 후속 줄 "이름 옆 표지나 별도 상태 칸"은 이름 옆 표지로 정한다.

이름 칸의 배치:

- 순서는 이름 단추, 자리 하나, "…" 메뉴 단추다. "…"는 항상 칸의 오른쪽 끝에 있다.

- 자리의 폭은 그 언어에서 세 문구 가운데 가장 긴 것에 맞춰 모든 행에 미리 잡아 둔다. 포인터가 행을 지날 때 이름이 줄어들거나 "…"가 옆으로 밀리면 안 된다. 행 높이도 그대로다.
- 자리는 "먼저 분석"을 쓸 수 있는 결과(실행 중이거나 일시 중지된 스캔)를 보는 동안에만 둔다. 끝난 결과에서는 자리가 없고 이름이 그만큼 넓어진다. 스캔이 끝날 때 한 번 바뀌는 것은 괜찮다.
- 표지는 공통 StatusBadge의 정보 색조이고 글자를 함께 쓴다. 행의 접근 이름에도 표지 문구가 들어간다.
- 이름이 길면 이름을 줄인다(NameText의 가운데 줄임). 표지와 단추는 줄이지 않는다.

"스캔 상태" 열이 생긴 뒤에도 표지는 이름 칸에 둔다. "먼저 분석 요청됨"은 사용자가 순서를 바꿔 달라고 한 요청이고, "스캔 상태"는 그 폴더를 읽은 결과(안을 읽지 못함, 다른 볼륨)다. 한 열에 섞으면 요청과 문제가 같은 것으로 읽힌다.

좁은 폭의 카드 배치: 표지는 이름 줄의 끝에 둔다. 카드에는 행 단추를 두지 않고 "먼저 분석"은 행 메뉴와 표 위 선택 동작 줄로 한다(포인터를 올릴 자리가 없다). "수정한 날짜"가 마지막 칸이 되어 한 줄을 차지하는 것은 받아들인다. 이름표와 값이 같은 줄에 있어야 한다.

측정에 따른 재결정:

구현 쪽에서 정한 네 가지에 대한 판단:

1. 스캔 중에 영역을 열었는데 보이던 판이 이미 바뀐 경우 "볼륨 관측 정보를 읽는 중"을 다음 판까지 유지: 받아들인다. 사용자가 한 일이 없는데 "더 이상 최신이 아닙니다" 오류를 보이는 것보다 낫다.
2. 스캔 중의 읽기 오류에 "다시 읽는 중…"을 보이고 다음 판에서 다시 읽는 것: 실행 중에는 받아들인다. 두 경우는 고친다(아래 "고칠 것" 2).
3. 영역이 열린 채 글자 선택을 풀면 최대 1초 뒤에 바뀌는 것: 받아들인다.
4. "다시 읽는 중…" 동안에도 "이 볼륨에서 스캔한 모든 폴더 비교" 단추를 남겨 초점을 지키는 것: 받아들인다. 그때 누르면 가장 새 판으로 동작한다.

고칠 것:

1. 비교의 기다림 한도를 2초로 바꾼다(위 재결정).
2. "다시 읽는 중…"이 끝없이 남지 않게 한다. 일시 중지 중에는 다음 판이 오지 않으므로 읽기 오류를 바로 보이고 "다시 시도"를 둔다. 실행 중에도 같은 영역의 읽기가 세 번 잇달아 실패하면 오류와 "다시 시도"를 보인다. 읽고 있지 않은데 "다시 읽는 중…"이라고 말하는 것은 틀린 안내다.

후속 (병합을 막지 않는다):

남은 틈 (후속, 병합을 막지 않는다): 실행 중에 판이 바뀌어 거절된 뒤 요약의 총계 읽기 자체가 실패하면, 다음 게시나 스캔 종료까지 "다시 읽는 중…"이 남는다. 스캔이 실행 중이라 다음 게시가 1초쯤 뒤에 오므로 짧게 끝난다. 요약의 읽기 실패 상태를 영역에 넘기는 수정은 탐색 표의 공통 부품을 만들 때 함께 넣는다.

## scan · paused · 처리 흐름

1. 분석 중 화면의 주인공은 실시간으로 자라는 그래프와 부분 결과다. 저장소별 진행 표가 화면 대부분을 차지하면 안 된다. 진행 카드 아래에 그래프를 두고, 저장소별 진행은 그 옆이나 아래의 접을 수 있는 영역으로 둔다.
2. 표의 기본 열은 저장소, 상태, 남은 폴더, 읽지 못한 위치 네 개다. 장치, 수집 방식, 모드·상한, 진행 중은 행을 펼쳤을 때 보이는 상세로 옮긴다.
3. 자원 사용 선택과 상한 입력은 표 머리 옆에 그대로 두되, 상한 입력은 "고급" 안으로 넣는다.
4. 2초 안에 움직임이 보여야 한다. 확인한 항목 수가 계속 올라가고, 지금 읽는 위치 한 줄을 진행 카드에 표시한다. 전체 개수를 모를 때는 진행 막대를 불확정 표시로 쓴다. 지금 그림의 고정 길이 막대는 백분율처럼 읽힌다.
5. 읽지 못한 위치 수(실패 열)는 숫자를 누르면 "읽지 못한 위치 보기"가 그 저장소로 걸러져 열린다.
6. paused: "연결이 끊겨 이 저장소의 수집을 닫았습니다" 행에는 "다시 연결해 이어서 분석" 동작이 필요하다.

## browse · 폴더 먼저 살펴보기

1. 동작 이름은 "먼저 분석"으로 한다. "먼저 살펴보기"는 사용자가 직접 들어가 보는 동작으로 읽힌다.
